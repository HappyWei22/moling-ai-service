# 本地 14B 模型对照报告（qwen2.5-14B）

> 目的：换一个**能在组长那台 A4000 16GB 机器上跑通**的模型，按上次完全相同的方式重跑 v2 评测集。
> 结论先说：**14B 相比 7B 是质变——错误放行 5→0、错误召回 30.4%→66.7%，但本轮跑在开发笔记本上（显存 8GB，62% 上卡），速度不代表 A4000。**

## 3. 14B 相比 7B：三条实质改善

**① 错误放行归零（5 → 0）。** 这是上次报告中唯一的硬红线。7B 把 5 条本该追问/拒收的需求判成 `complete`，其中 V2-V026 把用户说的 `7.5分钟` 改成 `15分钟`。14B 一条都没放过去。

**② 错误召回追平云端（30.4% → 66.7%）。** 46/69 与云端数字完全相同。7B 的问题是"看到错也不报"，14B 补上了这个能力。

**③ scene 漏填减半（39 → 23 条应填未填）。** 仍明显差于云端（2 条），但已从"系统性缺失"变成"部分缺失"。且 **23 条里 0 条幻觉、1 条值不同**——它还是"看到了没写进去"，不是瞎猜。

代价：**错误精确从 91.3% 降到 83.6%**（多报 6 个不存在的错误），且 **3 条样本比 7B 退步**（D001 / D062 / D064）。净变化仍是 +14 条（17 条变好、3 条变差）。

## 4. 14B 与云端的真实差距：不是提取，是状态判定

状态混淆矩阵（行 = 期望，列 = 实际）：

| | | complete | needs_clarification | conflict | invalid |
|---|---|---|---|---|---|
| **云端** | complete | **26** | 0 | 1 | 0 |
| | needs_clarification | 0 | **27** | 0 | 1 |
| | invalid | 0 | 5 | 9 | **29** |
| **14B** | complete | **21** | 0 | 3 | 3 |
| | needs_clarification | 0 | **26** | 0 | 2 |
| | invalid | 0 | 0 | 8 | **35** |

两个关键读法：

**① 14B 输在"把 complete 判成 conflict/invalid"（6 条）。** 27 条 complete 只对了 21 条。若这 6 条判对，14B 是 42/98（42.9%），与云端 48.0% 只差 5.1pp。字段准确率已经基本追平（occupation 99%、font 95.9%、duration 96.9%），差的就是"该放行的没放行"。

**② 但在 invalid 判定上，14B 反而优于云端（35/43 vs 29/43）。** 期望 `invalid` 的 43 条里：

| | 判 invalid | 判 conflict | 判 needs_clarification |
|---|---|---|---|
| 云端 | 29 | 9 | 5 |
| 14B | **35** | 8 | 0 |

云端把 14 条 invalid 降级成了 conflict / needs_clarification，14B 只降了 8 条。这一项 14B 领先 14pp，**是它在总分落后 11.3pp 的情况下仍能被考虑的原因**——它的错误方向更"安全"：宁可判死，不肯放行。

> 注意：本评测集的 `expected.status` 里 **conflict 为 0 条**。所有"含冲突短语"的样本都被标为 `invalid`（因为冲突无法自动消解，按 v2 协议一律拒收）。所以不要把这 8 条误读成"冲突识别能力"。

**③ E9（字段齐全却仍报 needs_clarification）对 14B 影响最小**：仅 3 条（云端 6、7B 7）。也就是说 14B 的 36.7% 不是被 E9 压低的。

## 5. 在 A4000 上能不能跑通

**能，且是全量上卡。** 依据是算术，不是猜测：

| 项 | 数值 |
|---|---|
| 模型权重（`ollama list` 实测） | 9.0 GB |
| 4K 上下文 KV + 运行时开销 | 约 1.5–2 GB |
| A4000 显存 | **16 GB**（可用约 15.5 GB） |
| 结论 | **占用约 11 GB < 15.5 GB → 100% GPU** |

两条旁证：

1. **更小的 8 GB 显存都跑通了 98/98、技术失败 0**，16 GB 是严格超集——可行性没有疑问，只有速度差异。
2. 本批 62% 上卡时 6.7 tok/s、5.43 s/条。按 `448 GB/s ÷ 9 GB × 0.55 ≈ 27 tok/s` 估算，A4000 全量上卡后约 **20–30 tok/s**，98 条约 **3–5 分钟**。**这是估算值，上机必须用 `bench_local_models.py` 实测。**

> ⚠️ 不要让 4 核 Xeon 去 offload 任何层。本机 18 线程还能忍（6.7 tok/s），Xeon W-2223 只有 4 核，同样 offload 会掉到 1–3 tok/s。上机第一件事查 `ollama ps` 是否 `100% GPU`。

## 6. 结论与建议

**可以直接用的部分**：14B-Q4 在 A4000 上跑得通、错误放行 0、召回追平云端。作为"本地部署兜底方案"已经成立。

**但仍不能替代云端**：全一致 36.7% vs 48.0%，主要差在 6 条 complete 被误判为需要冲突/拒收。这会让用户多被追问一次，体验损失小于"错误放行"，但仍是缺陷。

**下一步性价比最高的两件事**：

1. **在 A4000 上重跑同一批**（模型、提示词、样本全不变），只换硬件。预计全一致数字不变或略升（温度 0，输出应基本一致），但**速度从 5.4 s/条降到 1.5–2.5 s/条**，才有实用价值。
2. **针对"complete 被判 conflict/invalid"的 6 条做提示词微调**，单独成批、单独记 sha。不要动已经 0 放行的判断逻辑。
