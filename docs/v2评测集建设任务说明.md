# 墨灵 v2 正式评测集建设任务说明

日期：2026-10-09  
交付对象：需求解析评测集建设组员  
适用模块：`POST /parse/v2`，以及解析完成后向 `POST /plan/v2` 的需求交接

## 1. 本次任务

请建设一套与当前 v2 需求解析协议一致、能够复核和重复运行的正式评测集。重点验证三件事：

1. 能否从用户原话中准确提取职业、场景、书体和单次练习时长。
2. 信息不足、非法值或冲突同时出现时，能否在一次回复中覆盖全部已识别问题，且不重复追问。
3. 用户多轮补充或明确修正后，能否根据完整会话得到正确结果。

本任务不是把 v1 样本中的 `style` 批量改名后直接交付。需要重新审核标准答案、补充 v2 特有场景、完成交叉复核，再冻结评测集。

本文第 2—4 节说明当前已实现的协议与行为；第 5—9 节规定本次建集和交付要求。样本规模、覆盖配额和复核比例是本次任务新增要求，不代表仓库此前已有这些规定。验收评测集质量与验收模型效果分开进行，不预设模型一定能通过全部样本。

## 2. 从 v1 到 v2，我们修改了什么

这里的 v1 指旧 `/parse` 和 `prompt_v1.md` 的需求解析协议；旧样本包的“v1.2”是标注包版本号，不能与解析协议 v2 混淆。

| 维度 | v1 | 当前 v2 | 对评测集的影响 |
|---|---|---|---|
| 输入 | 主要按一句用户原话建样本 | 输入为后端合并的本次会话完整用户原话，可包含多轮回答 | 增加多轮补充、修正与未解决冲突用例 |
| 书体字段 | `style` | `font`，仍表示书体名，不是字体文件名 | 标准答案、错误字段名、评测代码同步改为 `font` |
| 提取范围 | 职业、场景、书体、时长、目标、排除项 | 职业、场景、书体、时长 | 不再要求输出 `goal`、`exclusions` |
| 完成条件 | 书体、时长齐全，职业／场景／目标至少有一项 | 书体、时长合法，职业／场景至少有一项，且无错误 | 仅有目标的旧 `complete` 样本须改判 |
| 解析时长 | 保留明确的正整数；20 分钟等可能解析完成，但被规划侧拦截 | 解析阶段仅接受 5、15、30 分钟；其他明确时长为非法值 | 20、1、60、600、1440 等旧边界样本须重新标注，不能沿用旧 `complete` |
| 不支持的书体 | `unsupported_style_value`，字段为 `style` | `invalid_value`，字段为 `font` | 草书等仍判 `invalid`，错误类型和字段名发生变化 |
| 追问生成 | 模型输出 `follow_up`，本地也有兜底 | 模型不输出 `follow_up`；本地补缺失、去重并生成 `message` | 分别评估模型提取／错误识别与最终追问 |
| 多问题处理 | 缺失项按优先顺序追问，旧评测主要检查一条 `follow_up` | 一次汇总全部已识别问题，非法／冲突字段不重复报缺失 | 必须标注完整问题集合，检查漏问、重复问、多余问 |
| 个性化追问 | 职业、场景、目标全空时追问 | 职业和场景均空时，问一条“职业或书写场景”组合问题 | 不分别要求职业和场景，也不以目标替代两者 |
| 状态裁定 | 模型状态结合旧版本地规则 | 本地根据汇总问题裁定：`invalid > conflict > needs_clarification`，无问题才 `complete` | 混合问题不能只比较一个状态，还要比较全部问题 |
| 对外响应 | 返回旧 `UserRequirement` 结构 | HTTP 200 的业务响应为 `code/message/data`；未完成时 `code=400,data=null` | 内部标准答案与 API 响应分开标注 |
| 规划交接 | 计划输入使用旧需求结构 | 完成后的 `data` 提交 `/plan/v2`；服务内将 `font` 映射为计划字段 `style` | 不要把计划输出的 `style` 也改成 `font` |

以下原则没有改变：只提取用户明确表达的信息，不默认书体和时长，不从职业推断场景，不从场景推断职业，不擅自替用户选择或改值。楷书、行书、行楷的支持集合也没有改变。

## 3. v2 的三层结果必须分清

### 3.1 模型原始输出

提示词要求输出六个字段：

```json
{
  "occupation": null,
  "scene": null,
  "font": null,
  "duration_minutes": null,
  "status": "needs_clarification",
  "errors": []
}
```

模型负责提取字段、识别非法值和语义冲突。`errors` 记录所有非法值和冲突；缺失项由本地统一检查。不能要求模型生成 `follow_up`，也不能要求它输出旧 `goal/exclusions/style`。

### 3.2 本地最终解析结果

本地归一化字段、合并问题、去重、裁定状态并生成追问。最终需求对象只含五个字段：`occupation、scene、font、duration_minutes、status`。最终问题集合可存入评测标注，但不是对外需求对象的字段。

职业别名明确支持“老师→教师”“小学生→学生”；书体别名明确支持“楷体→楷书”“行楷体→行楷”。中文时长及单位表达应覆盖“十五分钟→15”“半小时→30”；换算后不在 5／15／30 内的明确时长仍为非法值，不能静默映射到最接近档位。

### 3.3 API 对外响应

| 情况 | HTTP | 业务结果 |
|---|---:|---|
| 解析完成 | 200 | `code=0,message="ok"`，`data` 为五字段需求对象 |
| 缺失、非法或冲突 | 200 | `code=400`，`message` 覆盖全部已识别问题，`data=null` |
| 请求校验或模型输出格式失败 | 422 | 技术错误，不能当作普通追问 |
| 模型调用／网络／超时失败 | 502 | 技术错误，单独报告 |
| 模型配置失败 | 503 | 技术错误，单独报告 |

未完成时，对外 `data=null`，因此字段和内部状态评测需要直接获取解析函数结果；不能从 API 的 `data` 读取这些字段，也不能将业务 `code=400` 当作 HTTP 400。

## 4. 标注规则与迁移示例

### 4.1 核心判定规则

1. 完成条件：`font` 合法且非空、`duration_minutes` 为 5／15／30、`occupation` 或 `scene` 至少一项非空，并且不存在非法值或冲突。
2. 未提供必需信息：标记 `missing_field`。职业和场景都没有时，字段标为 `personalization`，只算一个问题。
3. 提供明确不支持的书体或时长：该字段置空，标记 `invalid_value`，保留原始值或原话证据。
4. 同时要求互相冲突的合法值：该字段置空，标记 `conflicting_values`，不能自行挑选一个。
5. 状态按 `invalid > conflict > needs_clarification` 裁定；状态只能有一个，问题可以有多个。
6. 同一字段已经存在非法值或冲突时，不再因该字段为 null 追加缺失问题。同类同字段问题去重，但不同字段的问题不能丢失。
7. 多轮输入中，后续回答可补充或明确修正先前回答。明确“改成”“刚才说错了”的修正不能机械判成冲突；单纯同时要求两个值也不能机械采用最后一个。

### 4.2 组员必须掌握的例子

| 用户输入 | v2 期望 | 迁移／考点 |
|---|---|---|
| 我是老师，楷书，每次15分钟。 | `occupation=教师,font=楷书,duration_minutes=15,status=complete`，场景为空 | 只提供职业也能完成 |
| 写作业用，楷体，每次15分钟。 | 职业为空，场景取用户原话，`font=楷书,status=complete` | 只提供场景也能完成；别名规范化 |
| 想改善工整度，楷书，每次15分钟。 | 职业、场景为空，`status=needs_clarification`；问职业或场景 | v1 的目标曾能满足个性化条件，v2 已取消 |
| 我是学生，楷书，每次20分钟。 | 时长为空，`status=invalid`；问用户改为支持时长 | v1 可保留 20，v2 不可 |
| 每天练-10分钟。 | `status=invalid`；问题为书体缺失、时长非法、职业或场景缺失 | 一次覆盖三个问题；不能再重复问“时长缺失” |
| 楷书和行书，每次15分钟。 | 书体为空，`status=conflict`；问书体冲突及职业或场景 | 冲突不免除其他缺失追问 |
| 想练楷书和行书，每次-10分钟。 | `status=invalid`；书体冲突、时长非法、职业或场景缺失 | 最高优先级状态与完整问题集合同时正确 |
| 我是学生，练楷书，每次15分钟。后来补充：改成行楷。 | `font=行楷,status=complete` | 明确修正覆盖先前值 |
| 我是学生，练楷书，每次20分钟。后来补充：刚才说错了，每次15分钟。 | 时长为15，`status=complete`，不保留已纠正的非法问题 | 多轮纠错后可正常完成 |

### 4.3 不得自动继承的旧规则

- v1 中“仅有目标”“非标准正整数时长”“非空排除项”的结论均需重审。v2 没有 `exclusions` 字段，也没有以它为空作为规划门禁的协议，不能照搬旧 `plan_gate=block`。
- “想练楷书，但不要练楷书”虽然不再输出排除项，仍涉及语义矛盾；应登记裁决，明确它在 v2 中的错误字段、置空行为和追问，不能直接删除矛盾，也不能照搬 v1 两字段保留方式。
- v1 扩展职业／场景词表不自动成为 v2 的权威词表。当前 v2 未完整搬入旧场景映射词表，场景的等价表达应在指南中列出允许答案；不得为了通过字符串比对强行改写用户意愿。
- “随便你选”“毛笔字”“一会儿”“15到20分钟”“楷书和草书并列”“多个职业或多个场景”等边界，须逐类核对当前提示词与实现。口径不足时先记争议、完成裁决，再进入正式集。
- 标准答案应按确认的协议独立标注。若实际模型输出不符合规则，记模型失败；不能用模型输出反向修改答案。

## 5. 样本规模、覆盖与分集

本次交付至少 100 条有效评测输入，按约 60% dev／20% val／20% sealed 分集；100 条时目标为 60／20／20。分配单位是语义组，不能拆组凑配额；超过 100 条时说明实际数量及比例。

| 覆盖维度 | 本次最低要求 |
|---|---|
| 完整需求 | 三种书体、三档时长均覆盖；含仅职业、仅场景、职业和场景都有 |
| 缺失 | 单项缺失、两项缺失、全部必需信息缺失均覆盖 |
| 非法 | 不支持书体、非标准正整数、负数、0、小数、单位换算后不支持均覆盖 |
| 冲突 | 至少 6 条真实合法值冲突，覆盖书体和时长；每个分集均有冲突样本 |
| 多问题组合 | 至少 15 条，含多项缺失、多个非法字段、冲突＋缺失、非法＋缺失、非法＋冲突＋缺失 |
| 多轮 | 至少 20 条输入检查点，来自至少 8 个会话；含补齐、明确改口、非法值纠正、冲突消解、补充后仍未完成 |
| 表达变化 | 简短列表、语序变化、口语、别名、中文数字、否定表达均覆盖 |
| 禁止推断 | 至少 6 条，检查职业／场景互推、默认书体、默认时长、以目标替代场景 |

以上维度可以重叠计数。三种书体与三档时长应至少在完整需求中覆盖各自全部取值，不要求机械生成全部笛卡尔积。

分集纪律：

1. 同义改写、近重复、同一会话各轮检查点必须进入同一分集；同一 `semantic_group` 不得跨集。
2. dev 用于调试和修复；val 用于阶段验证；sealed 只用于冻结后的最终评估。
3. sealed 至少覆盖完整、缺失、非法、冲突、多问题组合和多轮场景。旧版封存集冲突覆盖为 0 的缺口不能带入新集。
4. 新 sealed 优先使用独立新建语义组，不使用已经拿来调提示词、讨论失败或展示示例的内容。旧 sealed 的迁移须由原负责人按原封存纪律处理，普通迁移只处理旧 dev／val。
5. 冻结后不得用 sealed 挑错、改提示词或反复试跑。同一冻结版本最终整批评估一次，记录版本、访问和结果；更改样本须登记原因并重新冻结。
6. 样本包版本、协议版本、模型版本分别记录。不要覆盖旧 v1 样本与历史结果。

## 6. 每条样本的存储格式

采用 UTF-8 JSONL，一行一个对象。下面定义的是评测数据格式，不是 API 请求格式，也不是对外响应结构。

```json
{
  "id": "V2-D001",
  "protocol_version": "v2",
  "split": "dev",
  "semantic_group": "V2-G001",
  "tags": ["invalid", "multi_issue", "missing_font", "missing_personalization"],
  "input": "每天练-10分钟。",
  "conversation_id": null,
  "turn_index": null,
  "user_turns": ["每天练-10分钟。"],
  "source": {"kind": "new", "v1_id": null},
  "expected_requirement": {
    "occupation": null,
    "scene": null,
    "font": null,
    "duration_minutes": null,
    "status": "invalid"
  },
  "expected_model_errors": [
    {"type": "invalid_value", "field": "duration_minutes", "value": -10}
  ],
  "expected_issues": [
    {"type": "missing_field", "field": "font", "value": null},
    {"type": "invalid_value", "field": "duration_minutes", "value": -10},
    {"type": "missing_field", "field": "personalization", "value": null}
  ],
  "expected_api": {"http_status": 200, "code": 400, "data": null},
  "message_check": {
    "required": ["询问书体", "要求修改非法时长", "询问职业或书写场景"],
    "forbidden": ["重复询问时长缺失", "分别强制补职业和场景", "直接生成计划"]
  },
  "rationale": "时长明确但非法，另缺书体与职业或场景；三个问题均须提示。",
  "evidence": {"duration_minutes": "-10分钟"},
  "annotator": "填写实际标注人",
  "reviewer": "填写实际复核人"
}
```

补充要求：

- `expected_requirement` 是本地最终需求标准答案；`expected_model_errors` 只含模型应识别的非法／冲突，`expected_issues` 包含本地补齐后的完整问题集合。
- `expected_api`：完成样本的 `data` 填五字段对象，并写 `code=0,message="ok"`；未完成样本的 `data=null`，追问要求放入 `message_check`。
- 多轮样本同时保留 `user_turns`、会话编号、当前轮次和实际提交的合并 `input`，只包含截至当前轮的内容，不能把未来回答提前放入输入。合并格式与后端约定一致，并在指南中写明。
- 同一会话可建多个检查点；每个检查点一条记录。统计时同时报告输入条数、独立会话数和语义组数，不能把改写／多轮检查点都算成独立用户。
- 迁移样本的 `source.kind=migrated`，记录原 v1 编号，并在迁移表写清字段、状态、问题、规划结论的变化。
- `errors.value` 的数字／字符串表示及冲突原话允许等价形式要写入指南。问题匹配主要按 `type+field`，原值／证据另外核验。当前脚本对原值和非空字段使用精确比较；若指南允许等价表达，须同步扩展评分规则后再使用，不能仅在文档中声明放行。
- 技术错误注入属于接口契约测试，另存测试文件，不混入自然语言理解样本数。

## 7. 复核与自动校验

1. 先用 dev 中 10 条覆盖各类场景的样本做双人独立预标注，记录分歧，完善指南。
2. 所有正式样本必须由第二人复核。封存样本由指定建集／复核人员处理，调提示词人员不参与读取封存内容。
3. 模糊表达、修正与冲突边界、旧排除项矛盾、职业／场景归一化均进入争议裁决表。未解决项进入候选池，不纳入正式冻结集。
4. 提交实际标注人、复核人、一致性统计及裁决记录，不得把尚未进行的复核写成通过。

自动校验脚本至少检查：

- JSONL 可读、编号唯一、字段类型与 v2 结构正确，五字段答案无旧字段。
- 非空 `font` 和时长符合枚举，完成条件与状态优先级一致。
- 非法／冲突字段置空，缺失问题完整，同字段不重复报缺失。
- `expected_model_errors` 与完整问题集合一致，原值／证据可追溯。
- API `code/data` 与内部完成状态一致。
- 分集比例、语义组隔离、会话隔离、各维度覆盖配额符合要求。
- 输入无精确重复；近重复检查结合人工复核，不能仅凭不同字符串认定无泄漏。
- 清单数量和哈希匹配，正式集无未裁决争议。

校验报告必须由脚本产出，人工复核结论另附记录。通过自检不等于证明真实模型全部正确。

## 8. 配套评测与结果要求

**组员完成评测集并通过数据校验、交叉复核后，必须使用该评测集运行一次完整的 dev／val 真实模型批量测试，再提交交付包。只提交样本文件，或只跑 mock 自检，不算完成本任务。** 建集执行人负责组织测试和整理结果，复核人负责检查追问语义与报告；实际人员姓名在交付 README 中填写。

`parsing.run_parse` 已支持 v2 批量评测，使用 `--protocol v2` 显式切换。默认仍为 v1，兼容历史评测；仅设置环境变量中的提示词版本不会切换批评测协议。v2 使用 `parse_text_v2` 和独立评分逻辑，必须显式提供按第 6 节格式编写的 v2 样本，旧版样本不自动转换。

### 8.1 完成建集后的必做测试步骤

1. 确认第 7 节的数据校验及双人复核已完成，保存本次测试使用的样本版本与哈希。
2. 在项目根目录使用项目虚拟环境，确认模型密钥已配置；密钥不写入样本、报告或交付包。
3. 先运行下方 mock 命令验证工具链，再执行真实模型命令，完整运行本次正式集的 dev／val。不能用 `--limit` 抽查结果替代完整测试。
4. 检查运行记录条数与 dev／val 清单条数一致，每条样本都有结果或明确的技术失败记录。批次被阻止启动（退出码 2）或中途未完成时，排查后重新运行，保留各批次记录。
5. 复核全部实际追问的 `message`，按 `required/forbidden` 逐条记录漏问、重复问、多余问和语义结论；另外汇总最终端到端成功率。
6. 整理失败清单，区分模型理解、标注口径、本地汇总及技术调用问题。确认标注有误时走复核／裁决流程，更新版本后重测；模型失败如实保留，不通过删样提高分数。
7. 随交付包提交运行命令、模型／提示词／代码版本、运行记录、自动报告、人工复核记录和失败分析。测试发现失败可以交付，但必须说明结果与未解决问题，不能将“已完成测试”写成“模型全部通过”。

真实模型开发／验证评测命令（项目根目录执行；正式样本放在下方指定路径）：

```bash
.venv/bin/python -m parsing.run_parse --protocol v2 --client real \
  --samples v2_eval/samples_v2.jsonl --splits dev,val \
  --out v2_eval/baseline/dev_val_runs.jsonl \
  --report v2_eval/baseline/dev_val_report.md --tag v2-baseline
```

无需密钥的流程自检：

```bash
.venv/bin/python -m parsing.run_parse --protocol v2 --client mock \
  --samples parsing/fixtures/v2_smoke_samples.jsonl \
  --mock-file parsing/fixtures/v2_smoke_responses.json \
  --out /tmp/moling-v2-smoke-runs.jsonl \
  --report /tmp/moling-v2-smoke-report.md
```

上述命令适用于当前项目虚拟环境；其他环境使用已安装项目依赖的 Python。正式样本尚未交付时，真实模型命令中的路径是组员需要建立的交付路径。每次重测使用独立的批次目录或文件名，避免覆盖前次证据。

**本次组员建集后测试只要求 dev／val，封存集不作为日常测试对象。** 封存最终评估在版本冻结且获得授权后另行进行；建集后必须测试的要求不代表允许提前运行 sealed。

### 8.2 评分与复核口径

仓库附带的两条 smoke 样本只用于检验工具链，不是正式评测集，也不计入第 5 节的数量与覆盖配额。组员另建 mock 文件时，格式为 `{"responses":{"完整输入文本":"模型六字段 JSON 字符串"}}`；响应应代表模型原始输出，不是 API 包装。`test_parse_v2.py` 和 `test_eval_v2.py` 的模拟模型输出只验证契约与评测流程，不能替代真实模型评测。

脚本支持 JSON 数组或 JSONL、`--splits` 过滤、`--limit` 开发抽查、`--append` 非封存追加。v2 默认输出到 `parsing/parse_runs_v2.jsonl`，建议始终显式指定每批输出路径。封存默认拒绝运行；只有获得最终评测授权后才可使用 `--allow-sealed`。封存不能搭配 `--limit` 或 `--append`，必须整批评测。标志位不代替审批与访问登记，脚本也不自动批准访问或判断历史运行次数。

退出码：`0` 表示自动检查全部一致，`1` 表示存在自动检查不一致或单样本技术失败，`2` 表示样本、配置或封存保护阻止批次启动。**退出码 0 不代表追问语义已经全部通过人工复核。**

评测至少报告以下指标，并写明分母：

| 指标 | 口径 |
|---|---|
| 字段准确率 | 职业、场景、书体、时长逐字段比较，null 也计入；只在成功得到本地解析结果的样本上统计，并同时报告解析失败数量 |
| 状态准确率 | 本地最终状态与标准答案比较，按四类状态分别报告 |
| 模型错误识别 | 非法／冲突问题的召回率、精确率，匹配 `type+field`，另核验原始值 |
| 完整问题集合命中率 | 实际问题集合与期望集合完全一致的样本占比 |
| 最终追问覆盖 | 检查 `message` 是否表达每个应处理问题，统计漏问、重复问及多余问的样本占比；不能仅以关键词出现代替语义判断 |
| 错误放行率 | 标准答案未完成的样本中，实际返回 `complete`／业务成功的比例 |
| 端到端成功率 | 全部已运行样本中，技术执行成功且字段、状态、问题集合、API 响应及追问均符合要求的比例；技术失败计为未成功 |

字段空值多时，额外报告非空标准答案的准确率，避免大量 null 掩盖提取失败。技术失败按 config／transport／format 分层，不能只从分母排除后宣称整体成功。

追问以语义完整性为主；需要锁定固定话术时另报逐字一致率。报告按 split、状态、多问题组合、多轮、迁移／新建来源分桶，dev、val、sealed 分开呈现。附失败清单与归因，禁止将三集合混算成最终封存成绩。

当前脚本自动保存字段差异、模型错误及原值比较、完整问题集合差异、原始六字段契约检查、模型状态与最终状态检查，以及按解析结果构造的 API 响应检查。报告按分集、状态、tags 和来源分桶，并显示技术失败与错误放行率。

`message_check.required/forbidden` 是人工语义复核要求，脚本原样保存，不拿这些中文要求做子串匹配。可另加 `contains/not_contains` 字符串列表用于机器检查；也可在 `expected_api.message` 写固定期望全文。字符串检查不能替代语义复核。自动满足要求但追问未复核的样本，其 `end_to_end_match=null`、`message_review=pending`，不得按已完成的端到端成功计分。复核人须另外提交逐条漏问、重复问、多余问判断与最终成功率。

API 检查由内部解析结果构造，没有发起实际 HTTP 请求；真实 HTTP 状态、请求校验和响应序列化仍须通过接口契约测试核验。脚本基础校验涵盖五字段答案、状态／问题一致性、重复问题、相同输入／语义组／会话跨集和 API 业务结果；数量配额、近重复、实际人审与封存历史访问仍由建集校验脚本和复核记录完成。

运行记录保存样本哈希、代码提交号及工作区修改标记、解析／评测代码哈希、模型名称、关键参数、提示词版本及完整哈希、运行时间、命令、实际输出与失败原因。样本包版本和复核快照另在交付 README 中固定。真实模型基线先跑 dev／val；封存最终运行须按封存访问流程批准并登记。本次文档不授权提前读取或运行旧封存样本。

建议交付目录：`v2_eval/`。请一次交付完整包：

| 文件 | 必须包含的内容 |
|---|---|
| `samples_v2.jsonl` | 正式样本、完整标准答案、问题集合、证据和复核信息；dev／val／sealed 物理分开保存更便于隔离 |

| `scripts/` | 建集数量／覆盖／近重复校验、清单生成脚本；附现有 `parsing.run_parse --protocol v2` 使用说明 |
| `校验报告.md` | 自动校验结果、覆盖度、去重与隔离检查、双人复核证据 |

评测集验收条件：有效条数及覆盖达到第 5 节要求；全部正式样本已复核、无未决口径；自动校验通过；无跨集语义组／会话泄漏；封存可追溯；迁移说明清楚；完整 dev／val 真实模型批量测试已执行，运行条数与清单一致；实际追问均已人工复核；运行证据、指标与失败分析齐全，v2 评测可以复现。模型未通过的样本应保留并据实报告，不是删样理由。缺少真实模型测试或追问人工复核时，交付状态标为未完成，不得仅凭 mock 结果或退出码 0 宣称通过验收。

本任务未指定模型上线通过阈值、组员姓名或截止日期；由项目负责人安排并在交付 README 中回填。不要自行编造“已批准”“已复核”“已通过”的记录。
